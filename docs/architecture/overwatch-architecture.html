Overwatch — Fraud Rule Engine

Architecture & implementation plan for the interview assignment.
A system that ingests categorized transaction events, applies configurable fraud rules, and surfaces flagged activity through a real-time dashboard.

Java 25 · Spring Boot 4 Redpanda · PostgreSQL React + Vite Docker Compose ZAR · South African context
01

Architecture overview

Three services, one event bus, one database. Each service has a single responsibility and communicates only through Redpanda topics or the PostgreSQL store. The frontend talks exclusively to the BFF — never directly to the engine.

02

Tech stack decisions

DECIDED
Java 25 (LTS) + Spring Boot 4.1 + Maven — Both on current supported lines, not trailing ones. Spring Kafka for the event pipeline, Actuator + Micrometer for Prometheus metrics, and virtual threads for the engine's per-transaction concurrency.
DECIDED
Redpanda over Kafka — Kafka-API compatible, single binary, no ZooKeeper. The Spring Kafka client works unchanged against it. Docker image is ~150MB vs Kafka's 500MB+ with ZK. One container instead of two.
DECIDED
PostgreSQL 16 — Battle-tested, rich querying for analytics aggregations (window functions, CTEs for velocity checks). JSONB columns for flexible transaction metadata. Interviewers know it immediately.
DECIDED
React 18 + Vite — Lightweight, fast HMR, minimal boilerplate. Recharts for charts (lightweight, React-native). Design tokens from i1 design system foundations.
DECIDED
3 services — transaction-simulator, fraud-engine, fraud-api. Clear separation of concerns. Each has its own Dockerfile. Composed via docker-compose.yml.

Service breakdown

⚡ transaction-simulator

Generates realistic synthetic transaction events on a configurable schedule and publishes them to Redpanda.

Port: 8081 Topic: transactions Rate: configurable TPS Data: merchants, categories, amounts, locations, card types
🛡 fraud-engine

The core. Consumes transactions, runs them through the rule pipeline, persists results, and publishes alerts for flagged activity.

Port: 8082 Consumes: transactions Produces: fraud-alerts Writes: PostgreSQL
📊 fraud-api

BFF for the dashboard. Serves REST endpoints for transactions, alerts, rules, and aggregated statistics. No business logic — pure data serving.

Port: 8080 Reads: PostgreSQL Serves: REST API Docs: OpenAPI / Swagger
04

Fraud rules design

Rules are configurable entities stored in PostgreSQL, not hardcoded logic. Each rule has a type, parameters (as JSON), a severity, and an enabled flag. The engine loads rules on startup and can reload via an API call — no restart needed.

Rule Logic Parameters Severity
High Value Amount exceeds ZAR threshold {"threshold": 50000.00} HIGH
Velocity Check N+ transactions within M minutes {"count": 5, "windowMinutes": 10} HIGH
Late Night Transaction outside business hours (SAST) {"startHour": 23, "endHour": 5, "tz": "Africa/Johannesburg"} MEDIUM
Round Amount Suspiciously round ZAR number {"minAmount": 5000.00} LOW
Cross-Border Transaction from outside South Africa {"homeCountry": "ZA", "watchList": ["NG","RU","CN","BR"]} HIGH
Category Mismatch Merchant category vs cardholder profile {"flaggedCategories": ["crypto","gambling","forex"]} MEDIUM

The rule engine uses a Strategy pattern — each rule type implements a FraudRule interface with an evaluate(Transaction) method. A RuleEngine orchestrator runs all enabled rules against each transaction and collects results. A transaction can trigger multiple rules; each hit produces a separate FraudAlert record with a composite risk score.

// Strategy pattern — clean, extensible, testable
public interface FraudRule {
    String getRuleType();
    Optional<FraudAlert> evaluate(Transaction txn, JsonNode params);
}

@Component
public class RuleEngine {
    private final List<FraudRule> rules;

    public List<FraudAlert> process(Transaction txn) {
        return ruleConfigs.stream()
            .filter(RuleConfig::isEnabled)
            .map(config -> findRule(config.getType())
                .evaluate(txn, config.getParameters()))
            .flatMap(Optional::stream)
            .toList();
    }
}
05

Database schema

-- Core tables
CREATE TABLE transactions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    card_id         VARCHAR(64) NOT NULL,
    amount          DECIMAL(15,2) NOT NULL,
    currency        VARCHAR(3) DEFAULT 'ZAR',
    merchant_name   VARCHAR(255),
    merchant_category VARCHAR(64),
    country_code    VARCHAR(3),
    channel         VARCHAR(32),      -- POS, ONLINE, ATM, MOBILE
    timestamp       TIMESTAMPTZ NOT NULL,
    metadata        JSONB,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE fraud_rules (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            VARCHAR(128) NOT NULL,
    rule_type       VARCHAR(64) NOT NULL,   -- HIGH_VALUE, VELOCITY, etc.
    parameters      JSONB NOT NULL,
    severity        VARCHAR(16) NOT NULL,   -- LOW, MEDIUM, HIGH, CRITICAL
    enabled         BOOLEAN DEFAULT TRUE,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE fraud_alerts (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    transaction_id  UUID REFERENCES transactions(id),
    rule_id         UUID REFERENCES fraud_rules(id),
    rule_type       VARCHAR(64) NOT NULL,
    severity        VARCHAR(16) NOT NULL,
    risk_score      INTEGER CHECK (risk_score BETWEEN 0 AND 100),
    description     TEXT,
    status          VARCHAR(32) DEFAULT 'OPEN',  -- OPEN, REVIEWING, DISMISSED, CONFIRMED
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

-- Indexes for common queries
CREATE INDEX idx_txn_card_id ON transactions(card_id);
CREATE INDEX idx_txn_timestamp ON transactions(timestamp);
CREATE INDEX idx_alerts_status ON fraud_alerts(status);
CREATE INDEX idx_alerts_severity ON fraud_alerts(severity);
CREATE INDEX idx_alerts_created ON fraud_alerts(created_at);

Deferred decisions

These items are worth discussing but don't block the build. We can revisit as we progress.

DEFERRED WebSocket for real-time alerts — SSE or WebSocket push from BFF to dashboard? Or just poll every 5s? Polling is simpler and likely sufficient for the demo.
DEFERRED Authentication — The brief doesn't mention auth. We could add Spring Security with a simple login screen (i1 has the template) or skip it. Likely skip for scope.
DEFERRED Risk scoring algorithm — Simple additive (sum of rule severities) vs weighted (configurable weights per rule). Start simple, mention the extension point.
DEFERRED Redpanda Console — Redpanda ships a web UI (port 8088). Include it in Docker Compose for debugging? Low cost, nice to have.
DEFERRED Flyway migrations — Use Flyway for DB migrations vs init script? Flyway is more professional but adds a dependency. Probably worth it.

13

Interview talking points

Why Strategy pattern for rules? — Open/closed principle. New rule types don't touch existing code. Each rule is independently testable. The engine doesn't know or care what rules exist.
Why Redpanda over Kafka? — Same API, fraction of the operational complexity. Shows pragmatism — you don't always need the heaviest tool.
Why separate BFF? — The engine is a hot path (processing every transaction). The API serves dashboard queries. Different scaling profiles, different SLAs. In production you'd scale the engine horizontally based on consumer lag.
Why not microservices for each rule? — Over-engineering for this scale. The Strategy pattern gives the same extensibility without the network hop, serialization cost, and deployment complexity.
Scalability story — The engine scales horizontally via Kafka consumer groups. Add more engine instances, Redpanda rebalances partitions. The API scales independently behind a load balancer. PostgreSQL handles the volume; for true scale you'd add read replicas or move analytics to a separate store.
